E3SM Land Model — code explorer

The analysis comes from SPEL, a Fortran parser and refactoring toolkit built for ELM. SPEL reads the model sources, walks the call tree of elm_drv with dummy arguments resolved to the fields actually passed at each call, and records every access, loop, filter and namelist gate along the way. This site is a browsable export of that analysis: nothing here was run, everything was read.

The goal is to make a large, heavily configured model legible: to answer "what does this routine depend on", "who computes this field and who needs it", "what changes when I flip this flag", or "which state has to be in the restart file" without reading a hundred files. It is meant for scientists adding or changing a process, for people porting or optimizing the code, and for anyone new to ELM who wants to see how the pieces fit.

ELM is large and has many configurations, and a static analysis has to make conservative choices (an unknown is treated as "may happen"). So please explore and report: a routine that looks wrongly pruned, a dependency that cannot be real, a category that disagrees with what the model does, or a view that would help. Open an issue or feature request on the SPEL issue tracker.

Pick a snapshot (an analyzed E3SM checkout) and a configuration in the toolbar; every page follows them.

Tree graph

The time step as a layered diagram: one box per routine, lines from a routine to the later ones that read what it wrote, rows by dependency. Click into any routine; filters that cannot overlap (lake vs. non-lake columns) are taken into account.

Variable trace

Follow a handful of variables through the step on one timeline: where each is read and written, when a computed value is next needed, and what is carried into the next step.

Diff mode experimental

Compare two configurations or two snapshots: reachable routines, flipped if blocks, access sets and categories.

Call tree

The same step as an expandable tree, pruned by the configuration, with each routine's arguments, accesses, namelist gates and source.

Variables

Every instance field and module variable classified as prognostic, diagnostic, intermediate, input or unused, with restart and history registrations and their mismatches.

Types

Derived types and their members by subgrid level, instances, type-bound procedures; add members to the trace from here.

Modules

What each module uses and what uses it, as a layered graph, plus per-module contents.

Filters

The subgrid filters the step builds, where, under which conditions, and which pairs are disjoint or nested.
